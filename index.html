The Complete Claude Code Guide —
Beginner to Pro

Claude Code is Anthropic's agentic coding tool that lives in your terminal: it reads your codebase, plans changes, writes code, runs tests, and even opens pull requests — all from a chat prompt. This guide takes you from never having opened it to using it like a power user, with every slash command, CLI flag, keyboard shortcut, and pro workflow documented.

1 · What is Claude Code?

Before the commands, understand the machine. Everything else in this guide builds on this mental model.

The one-paragraph version: Claude Code is an agentic AI coding assistant that runs in your terminal. Unlike a chat bot that answers and waits, it can read your files, edit code, run shell commands, use git, search the web, and call external services — chaining dozens of actions together to finish a task while you watch, redirect, or walk away.

The agentic loop

Every task runs through three phases that blend together: gather context → take action → verify results. A "fix the failing tests" request might look like:

  1. Run the test suite to see what's failing
  2. Read the error output
  3. Search for the relevant source files and read them
  4. Edit the files to fix the issue
  5. Run the tests again to verify the fix

You are part of the loop: press Esc to interrupt and redirect mid-task, or let it run. Claude Code is the harness around the model — it provides the tools, the context management, and the execution environment that turn a language model into a coding agent.

What Claude can access

📁 Your project

Files in your directory and subdirectories (plus other files with your permission).

💻 Your terminal

Any command you could run: builds, git, package managers, scripts. If you can run it, Claude can.

🌿 Your git state

Current branch, uncommitted changes, recent commit history.

📝 CLAUDE.md

A markdown file with your project's rules and conventions, loaded every session.

🧠 Auto memory

Notes Claude saves automatically as it learns your patterns and preferences.

🔌 Extensions

MCP servers (external tools), skills, hooks, and subagents you configure.

The built-in tools

CategoryWhat Claude can do
File operationsRead files, edit code, create new files, rename and reorganize

Key concepts you'll meet all session long

  • Sessions — each conversation is saved as plaintext JSONL under ~/.claude/projects/. You can continue, resume, fork, and rewind them.
  • Context window — everything Claude sees (conversation, files, tool output) fills a window. It auto-compacts when full. Managing context is the #1 pro skill (see Pro Workflows).
  • Checkpoints — before Claude edits files it snapshots them, so you can roll back any change.
  • Permission modes — control how much Claude may do without asking (see Permissions).
  • Print mode (-p) — run one-shot tasks non-interactively, perfect for scripts and CI.

2 · Install & Setup

System requirements

  • macOS 13.0+ · Windows 10 1809+ / Server 2019+ (native or WSL) · Linux (Alpine 3.19+ supported)
  • Internet connection (required — unless you're running the local Ollama setup)
  • No GPU needed — inference happens on Anthropic's servers

Install (one command)

$curl -fsSL https://claude.ai/install.sh | bash

Works on macOS, Linux, and WSL. On Windows PowerShell use irm https://claude.ai/install.ps1 | iex; on Windows CMD use curl -fsSL https://claude.ai/install.cmd -o install.cmd && install.cmd.

Other install methods:

Verify & update

$claude --version
$claude update
$claude doctor

claude doctor runs a read-only health check of your installation and settings — do this any time something feels broken.

3 · Your First Session

A 5-minute walkthrough that gets you from zero to your first real change.

On this page
  • Start & log in
  • Ask your first question
  • Make your first change
  • Use git
  • Essential commands

Step 1 — Start & log in

$cd ~/my-project && claude

You'll see the welcome screen. First time in this folder, Claude Code asks if you trust it — press Enter to accept. If you're not logged in, it walks you through browser login. You'll land at a prompt that looks like ❯.

Step 2 — Ask your first question

Claude Code explores the codebase with tools — you'll see it run searches and read files in real time:

❯What does this project do? How is the authentication flow structured?

Watch how it acts: it greps for auth files, opens them, and answers with citations. That's the agentic loop — it gathers its own context instead of making you paste everything.

Step 3 — Make your first change

❯Add proper error handling to the API client. Run the tests after.
  • Claude proposes tool calls (file edits, test runs) and asks for approval before executing them — press y to allow, Esc to interrupt.
  • It snapshots files before editing, so you can /rewind any change later.
  • Give it a verification loop: "run the tests after" closes the loop so it can self-correct.

Step 4 — Use git

❯Commit these changes with a descriptive message.

Claude runs git diff, writes a good commit message, and commits. Ask it to create a pull request and it'll branch, push, and open a PR with a summary.

🔌 MCP prompts

MCP servers can expose prompts that appear as commands. They use the format /mcp__<server>__<prompt> and are dynamically discovered from connected servers. Example: a GitHub MCP server exposing a "summarize repo" prompt appears as /mcp__github__summarize-repo. These are per-server — the exact list depends on which servers you connect.

Master tip: most commands are useless without context. The pro pattern is combining them: /plan → approve → implement → /diff to audit → /code-review --fix → /security-review → commit. Each command is one step in a repeatable pipeline.

7 · CLAUDE.md & Memory — make Claude remember

CLAUDE.md is Claude Code's memory file: plain markdown, loaded into every session automatically. This is the single highest-leverage file in your project — it turns Claude from "random helpful dev" into "a teammate who knows your conventions."

What gets loaded, and where

ScopeLocationWho sees it
Project memoryCLAUDE.md at the project rootAnyone running Claude Code in this repo
Personal memory~/.claude/CLAUDE.mdJust you, everywhere

Personal skills~/.claude/skills/Your reusable skill packs

Start with /init

❯/init

Claude analyzes your repo — language, build system, test runner, code style — and generates a starter CLAUDE.md. Then you edit it. Great CLAUDE.md files contain only what Claude can't figure out from code:

  • Commands: build, test, lint, dev-server startup ("use npm run dev, not vite")
  • Architecture & conventions: patterns, folder structure, design decisions and why
  • Gotchas & traps: "don't touch generated code in dist/", "the DB schema is owned by the API team"
  • Workflows: how features get done here — TDD? feature branches? PR checklist?
  • Compact instructions: what must survive context compaction
Don't: paste whole files or endless boilerplate into CLAUDE.md. Claude derives most of it from the code — bloated memory wastes context tokens on every single request, all session long. Keep it tight; /doctor will literally flag bloated CLAUDE.md files.

Rule files, global rules, and auto-memory

  • Rules — files whose names start with RULES_ (e.g. RULES_SCRIPTS.md) are auto-discovered: rules in the same or parent directories as the working file are attached when Claude works on it, rules for the current directory (like .claude/rules/RULES.md) attach at session start. user_rules_* and RULES_* in ~/.claude/ are always loaded.
  • Global memory — files ending in _global.md in memory directories (~/.claude/memory/, project .claude/memory/) are always loaded, no matter the directory.
  • Auto-memory — when enabled, Claude saves learned preferences and project facts on its own, reviewing them each session. Manage everything from /memory.
  • Filesystem notes — Claude also auto-loads "memory files" as it navigates: @TODO.md, @STYLE.md, README.md, LICENSE… (the @-prefixed ones are read as memory, not task instructions).
Pro tip: use @ as a shortcut — type @CLAUDE.md in the prompt to see it, and mention files by @path/to/file to load them into context on demand.

8 · Skills & Subagents

Skills — on-demand knowledge packs

Skills are folders containing a SKILL.md (markdown instructions) plus optional scripts, templates, and references. Claude reads a skill's frontmatter at session start (tiny token cost) and loads the full instructions when the task matches. They're the modern replacement for stuffing everything into CLAUDE.md.

Skill anatomy — a folder like .claude/skills/migration/SKILL.md:
---
name: migration
description: Review and execute DB migrations for this repo. Use when the task mentions migrations, schema changes, or alembic.
---
# Running migrations
1. Always inspect the latest migration file before applying…
2. Never run `alembic downgrade` against production…
  • Where they live: personal ~/.claude/skills/, project .claude/skills/, plugin skills, and ~30 bundled skills that ship with Claude Code (the ones behind /code-review, /simplify, /doctor…).
  • How they trigger: the description field decides relevance — Claude invokes skills automatically when it matches, and you can force one with /skill-name (their folder name becomes a command).
  • Manage: /skills lists them (press Space to toggle visibility, t to sort by token cost), /reload-skills rescans after edits.
  • Write your own: /add-dir <path> to add a skill directory for the session; set skills.directories in settings to persist. The fastest path is asking Claude to create one: "create a skill for our deployment process".

Subagents — parallel workers with fresh context

Subagents are specialized agents you define once and invoke by name. Each runs with its own fresh context — it doesn't see your long conversation, so it doesn't bloat your context window. Perfect for focused work you can delegate.

Define them in .claude/agents/ (project) or ~/.claude/agents/ (personal) as markdown with YAML frontmatter:

---
name: docs-writer
description: Writes and updates documentation. Use when the task involves READMEs, docs/, or comments.
tools: Read, Write, Edit, Glob, Grep
model: sonnet
---
You are the documentation specialist. Follow these rules:
- Match the existing doc tone (check a current doc first)
- Update the table of contents when you add sections
  • Invoke: ask Claude — "use the docs-writer agent to update the README" — or type @docs-writer <task>.
  • Frontmatter fields: name, description (triggers relevance), tools (which tools exist for it), model, mode (primary/subagent), plus permissions, hooks, plugins, contexts for advanced setups.
  • Built-in bonus: the explore subagent is Claude's internal codebase researcher — used automatically when a task needs to find things.
  • Wait, there's more: Claude Code 2.1.221+ includes codebase context agents — permanent per-branch agents that continuously index and update codebase docs, so your @agents dispatches always have fresh, verified context (also injectable into sessions via @AGENTS.md).
Rule of thumb: if a task is self-contained and doesn't need your conversation history (research a library, write tests for module X), delegate it to a subagent. Your context stays small, Claude stays sharp, and work happens in parallel.

9 · MCP — plug in external tools

MCP (Model Context Protocol) is an open standard that connects Claude Code to external tools and data: GitHub, Sentry, databases, browsers, internal APIs. An MCP server exposes tools (functions), resources (data), and prompts; Claude Code is the client that calls them. Think of it as plugins for your agent.

What you can do with MCP

  • Access services — pull issues/PRs from GitHub, query Sentry errors, run SQL against your DB, search internal wikis
  • Chain tools — Claude calls MCP tools like native tools, including after its own edits ("update the ticket with a link to the PR I just opened")
  • Rich auth — OAuth flows for remote servers (claude mcp login <name>), encrypted credentials for local ones
  • Security — MCP tools respect your permission settings: ask/allow/deny rules like mcp__github__*

Add a server (three scopes)

$claude mcp add my-server -- npx -y @my-org/mcp-server
$claude mcp add --transport sse my-server https://example.com/mcp

Scopes: --scope user (default, ~/.claude.json) · --scope project (.mcp.json, checked into the repo so teammates share it — pass --env values with ${VAR} placeholders to avoid committing secrets) · --scope local (.mcp.local.json, gitignored, your personal secrets).

10 · Hooks — automate around the agent

Hooks are scripts that run automatically at lifecycle events — before/after tools execute, on user prompts, at session start/end. They let you enforce guardrails (block edits to files matching a pattern), automate ceremony (auto-format after edits), and wire Claude into your own pipelines. The single most powerful customization Claude Code offers.

Events you can hook

EventWhen it firesCan block?
PreToolUseBefore a tool executes (Bash, Edit, Read…)✅ return exit code 2
PostToolUseAfter a tool completes—
NotificationBefore a notification is sent (telemetry, prompts)✅ (suppresses)
UserPromptSubmitBefore your prompt goes to the model✅ (stops submission)
StopClaude finishes responding—
SubagentStopA subagent finishes—
PreCompactBefore context compaction✅
SessionStartSession begins (after system prompt builds)—
SessionEndSession ends—
SetupInteractive setup / onboarding—
ConfigChangeSettings change while running—

Minimal example

// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "if echo \"$CLAUDE_TOOL_INPUT\" | grep -qE 'rm -rf'; then echo 'BLOCKED: destructive command' >&2; exit 2; fi"
          }
        ]
      }
    ]
  }
}
  • JSON mode: a hook can return JSON via stdout — the fields differ per event: decision (permission allow/deny/ask), permissionDecisionReason, continue, stopReason, systemMessage, additionalContext, suppressOutput.
  • Matchers: restrict hooks to specific tools (Bash, Edit, mcp__*) or user-prompt patterns (regex).
  • Environment: hooks receive rich context — CLAUDE_TOOL_INPUT, CLAUDE_PERCENTAGE_COMPLETED, CLAUDE_PROJECT_DIR, and more.
  • Debug: /hooks shows live configs; claude --debug --include-hook-events -p "…" traces hook execution. Hooks run with their own timeout (default 60s) and stop the session if they hang.

11 · Permissions & Security

Claude Code runs real commands and edits real files — so it's built around a permission system. Understanding it is what separates "letting the robot edit my repo" anxiety from confident daily use.

Permission modes

ModeBehaviorTypical use
default (a.k.a. manual)Prompts before file edits and bash commands; read-only tools run free; planned edits are batched into one approvalEveryday work
acceptEditsFile edits auto-approved; bash still asksFast iteration while you supervise
planNo file edits or bash — research and planning onlyExploration, architecture, safe mode
autoUses an LLM classifier to auto-allow safe commands; risky ones still askLong unattended runs
dontAskAuto-allows everything, except tools matching explicit deny rules; risky commands need an explicit allow ruleTrusted, tightly-configured setups
bypassPermissionsNo prompts at allCI, fully scripted runs (also --dangerously-skip-permissions)

Cycle modes with Shift+Tab; set per session with --permission-mode; persist defaults in settings (permissions.defaultMode).

Allow, ask, deny rules

Rules are strings with a tool name and an optional scoped pattern, e.g. Bash(npm run test:*), Read, mcp__github__*. They live in permissions.allow, .ask, and .deny in settings files:

{
  "permissions": {
    "defaultMode": "acceptEdits",
    "allow": [
      "Bash(npm run test:*)",
      "Bash(git status)",
      "Read",
      "mcp__github__*"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force)"
    ],
    "additionalDirectories": ["/home/samir/shared-lib"]
  }
}
  • Scoped rules (with parentheses) only match matching calls; unscoped tool names disable prompts for the whole tool.
  • Order: deny rules are evaluated before ask/allow; always_allow/always_ask settings take priority over allow/ask.
  • Git-diff awareness: Claude Code tracks whether it can see a file's git history — edits to files it can't diff (new, untracked, outside git) ask more conservatively.
  • Auto mode classifiers: auto mode uses model-based classifiers; they're user-editable (claude auto-mode config).
Reduce prompt fatigue: run /fewer-permission-prompts after a few sessions — it mines your transcripts and builds a personalized allowlist of the read-only commands you actually use.

Security best practices

  • Never run with --dangerously-skip-permissions on untrusted code. If a repo's .claude/settings.json or hooks look malicious, run claude --safe-mode.
  • Review third-party config: any repo you clone can ship CLAUDE.md instructions, settings, hooks, and MCP configs — they're code, and they execute. Anthropic's built-in protections don't cover malicious instructions; stay alert.
  • Hooks & MCP servers run with your privileges — only add ones you trust, keep them scoped (matcher, --env with ${VAR} placeholders), and pin versions.
  • Secrets: Claude Code encrypts credentials in ~/.claude/.credentials.json; use .claude/settings.local.json (gitignored) for personal config; check for leaked secrets with /security-review and the Claude Security plugin.
  • Sandboxing: /sandbox runs shell commands in an OS-level sandbox on supported platforms — extra defense for risky sessions.
  • Prevent unsafe tool calls with hooks: the PreToolUse hook is your guardrail: block rm -rf, block writes to protected paths, log every Bash command (see Hooks).

13 · Run Claude Code Free with Ollama

Yes, you can run the Claude Code interface with free, local models — no Anthropic API key, no subscription, fully offline. Since Ollama v0.14.0, Ollama exposes a native Anthropic-compatible API, so Claude Code can talk to it directly. Your code never leaves your machine. Perfect for learning, private code, and zero-budget development.

What this actually is: Claude Code (the agent harness — tools, file editing, terminal, UI) stays exactly the same. Only the brain changes: instead of Anthropic's cloud models, a local open-weight model serves the requests. The harness is model-agnostic; the model quality is what changes.

For agentic coding you need a model trained for tool calling — a general chat model will answer questions but fumble file edits. Verified picks:

3 · Point Claude Code at Ollama (native, no proxy)

Set three environment variables and start Claude Code with --model set to your pulled model:

$export ANTHROPIC_BASE_URL="http://localhost:11434"
$export ANTHROPIC_AUTH_TOKEN="ollama"
$export ANTHROPIC_API_KEY=""
$claude --model glm-4.7-flash

Ollama's Anthropic-compatible endpoint lives at http://localhost:11434 — the same port as its regular API. The --model name must match the tag you pulled.

4 · Make it permanent (settings.json)

No env-var juggling every session — put the configuration in ~/.claude/settings.json:

{
  "env": {
    "ANTHROPIC_BASE_URL": "http://localhost:11434",
    "ANTHROPIC_AUTH_TOKEN": "ollama",
    "ANTHROPIC_API_KEY": ""
  },
  "model": "glm-4.7-flash"
}

Now plain claude in any project uses your local model. Switch back to Anthropic's cloud by removing/commenting those keys (or override per-session with --model sonnet — but note the base URL still routes to Ollama, so use a separate profile or unset the env vars for cloud sessions).

5 · What works — and the honest caveats

✅ Works well

Interactive chat, file reading/searching, code generation, small edits, explain-code tasks, learning the Claude Code interface — all free and offline.

⚠️ Works, with effort

File editing and bash execution — depends entirely on the model's tool-calling quality. Use a tool-calling-trained model (the ones above).

❌ Struggles

Long multi-step tasks. The agentic loop is token-hungry; small models run out of context or start dropping tool arguments mid-task. Expect degraded behavior on big refactors.

🔇 Not available

Cloud features: web sessions, /schedule routines, ultrareview, /autofix-pr, Claude Design sync — anything running on Anthropic's infra.

  • Quality ceiling: a 7B local model is a different beast from Opus. Use this setup for learning, private code, and lightweight tasks — not as a free replacement for production AI coding.
  • Context is the bottleneck: Claude Code loads CLAUDE.md, skills, and system prompts on top of your conversation. Models below 32K context will feel cramped — prefer 128K-context models.
  • Tool-calling drift: sessions may degrade after many turns ("file edits truncate, tool calls drop arguments"). If a session gets weird, /clear and retry, or drop to a simpler task.
  • One brain at a time: some Claude Code features pick a "small fast model" for background tasks (ANTHROPIC_SMALL_FAST_MODEL) — keep it pointing at the same local model.

6 · Alternative: proxy bridges (if you need more model options)

Older tutorials use a translation proxy because Ollama didn't used to speak Anthropic's API. That's obsolete for Ollama itself, but proxies remain useful for other local engines (LM Studio ≥ 0.4.1, llama.cpp, vLLM — all also expose Anthropic-compatible endpoints now). The general pattern is the same: point ANTHROPIC_BASE_URL at the local server, set a dummy token, and pass the model via --model.

Don't break the trust flow: this is an unsupported, community setup — no Anthropic warranty, no cloud features, and you're responsible for what the model does. Use it on code you own. And if a tutorial tells you to install a random proxy and set ANTHROPIC_AUTH_TOKEN to a real credential, don't — dummy token only.

14 · Pro Workflows — using Claude Code like a power user

This is the section that turns "someone who knows the commands" into someone who ships. Everything here comes from the official best-practices guide plus how experienced users actually operate.

The core loop (respect it every time)

  1. Understand the codebase first — Claude Code explores automatically, but give it a good starting point: one specific, well-scoped task beats a vague paragraph.
  2. Plan before you build — for anything non-trivial, start in plan mode (Shift+Tab until "plan", or /plan <task>). Review its approach, correct it, then switch to implementation.
  3. Verify, don't assume — always ask for tests/verification: "run the tests after", "verify the change", "then run /verify". The model that checks its own work self-corrects.
  4. One task at a time — context is finite. Finish, commit, /clear, next task.

Prompting patterns that actually work

🎯 Specific beats generic

"Make the API client retry with exponential backoff, add a maxRetries config option, and test it" — beats "improve the API client".

📎 Point at files

Mention files with @src/auth.ts to load them directly. Claude reads less, starts faster, gets it right more often.

🔁 Loop the verification

"Write the code, run the tests, fix what breaks, and tell me what you changed" — a closed loop that ends with a summary.

🪤 State the traps

"Don't touch generated files in dist/", "the DB is Postgres, not SQLite" — your CLAUDE.md should carry these so you don't repeat them.

Follow-up discipline: instead of restating the whole task, give deltas — "now also handle the timeout case", "make the log message clearer". Claude Code tracks the conversation; keep your prompts short and directional.

The daily pipeline (my recommended rhythm)

  1. Start fresh: claude -c continues yesterday's session; claude starts clean. New task → new session.
  2. Explore: "Explain how X works in this repo" — let it read the code.
  3. Plan: /plan implement X — review the approach, adjust, approve.
  4. Build: implement with tests. Ask for commits at logical checkpoints.
  5. Audit: /diff to review every change, then /code-review --fix for a second pass.
  6. Secure: /security-review before opening the PR.
  7. Ship: "create a PR with a summary" — then /autofix-pr to babysit CI.

Context management — the real power skill

  • Watch your window: run /context when things feel sluggish. Big files, huge grep outputs, and long transcripts are the usual suspects.
  • Compact deliberately: /compact at natural milestones (not mid-thought). Put a "Compact Instructions" section in CLAUDE.md to steer what survives.
  • Delegate to subagents: /subtask write tests for the parser keeps your main context lean while work happens in parallel.
  • Ask side questions: /btw what's the Rust syntax for… answers without polluting the conversation.
  • Don't paste, point: @file references load exactly what's needed instead of dumping content into the transcript.

Parallel & long-running work

  • Fire and forget: /background (or claude --bg "task") to detach long work; monitor with claude agents.
  • Massive refactors: /batch decomposes a repo-wide change into parallel subagents, each in an isolated git worktree with its own PR.
  • Autonomy with a target: /goal all tests pass keeps Claude working until the condition is met.
  • Isolated experiments: claude --worktree experiment gives a disposable branch — perfect for risky changes.

Automation & scripting (print mode)

$claude -p "add docstrings to src/*.py" --allowedTools "Edit Write" --dangerously-skip-permissions
$gh pr diff | claude -p "review this diff for bugs, reply as JSON" --output-format json
  • CI code reviews: pipe PR diffs to claude -p with a review prompt and a --json-schema — structured findings straight into your pipeline.
  • Custom tools: combine --system-prompt (or append) with --allowedTools to turn Claude Code into a purpose-built CLI utility.
  • Cost control: --max-budget-usd 5 and --max-turns 20 keep unattended runs bounded; check /usage after.

CI with GitHub Actions

Official claude-code-action is available in the GitHub Marketplace for automating code review, fixing failing tests, and updating PRs. Long-lived tokens via claude setup-token (subscription plans) work in CI; API-key auth also works. Pair with --dangerously-skip-permissions only in sandboxed runners.

Remember: Claude Code is a tool, not an oracle. Its output is only as good as the context you give it, the verification you demand, and the guardrails you set. The pro isn't the one who trusts it most — it's the one who reviews, verifies, and engineers the loop.

15 · Troubleshooting

Diagnosis ladder

  1. /doctor — the built-in checkup: duplicate installs, PATH issues, unparseable settings, stale configs.
  2. /status — version, model, account, connectivity (works mid-response).
  3. claude doctor — read-only terminal diagnostics.
  4. claude --debug "api" -p "hello" — API-level request logs (categories: api, mcp, network, hooks, permissions, auto-mode…).
  5. claude --safe-mode — everything disabled; if it works, your config is the culprit. Bisect skills/hooks/plugins from there.
  6. claude logs <session-id> — recent output from a background session.
